How a step travels

Click any box to see what it does and which code does it. Numbers are per second, live.

Every step of every order goes round this loop once per attempt: claimed from PostgreSQL → written to the outbox in the same transaction → published to Kafka → executed by a worker → result back through Kafka → applied to the database, which makes the next step ready. The database is the single source of truth; Kafka only moves messages.

Steps run one at a time, in order: only the run's current step is ever eligible. When a step fails for good, FlowForge walks back over the steps that already succeeded and appends a compensation (undo) step for each one that declared it, most recent first — that is the lower lane.

    Counters

    Micrometer counters kept by EngineMetrics, also at /actuator/metrics/flowforge.*. They belong to this orchestrator instance and restart at zero with it; with two orchestrators each counts its own share.

    Leases and retries right now

    A claimed step holds a lease: if no result arrives before it expires, the recovery sweeper times the attempt out and retries it. A failed step waits in RETRY_WAIT until its backoff is over. Start Slow shipment or Flaky carrier to see these fill up.

    What the database holds

    Correctness: the 10 invariants

    ConsistencyChecker runs one SQL query per rule, all in one repeatable-read snapshot, and lists any rows that break it. It checks the history itself, so it would catch a bug however it happened — the stress tests run it after chaos. Re-checked every 5 s.

    Payment provider

    what the outside world saw

    A step can run more than once (a worker dies after charging, before reporting), so exactly-once can only come from the other side: the simulated provider (flowforge-payments) remembers every Idempotency-Key — FlowForge sends the step execution id — and answers a repeat with the original charge instead of charging again. Duplicates absorbed counts those repeats; orders charged twice must stay 0.

    Configuration of this instance

    Kafka keeps each topic as numbered partitions. Every message of a run has the run id as its key, so it always lands on the same partition and is read in order. A consumer group splits the partitions among its members; each member remembers how far it got (its committed offset), and lag = messages not yet processed. When a member dies, Kafka notices after the session timeout (10 s) and hands its partitions to the others — uncommitted messages are delivered again, which is why every step must be safe to run twice.
